# Shader Breakdown 17 — Lightning and Electric Arcs (Random-Walk Segment Rays)

Lightning/arcs are a 2D procedural effect built from a **random walk** that jitters a line into a branching arc, then renders the *distance to the polyline*. The math is a distance-to-segments combination, with a 1D random walk generating the jittered path.

## 1. The fragment (reconstructed key parts)

```glsl
float lightning(vec2 p, float seed){
    float t = 0.0;
    float d = 1e9;
    vec2 prev = vec2(-1.0, 0.0);        // start point
    for(int i=0;i<40;i++){
        vec2 cur = prev + vec2( (0.06) , jitter );   // random walk step
        float z = hash(i + seed);
        cur.x = mix(prev.x, cur.x, ...) ;            // jitter position
        cur.y += (z - 0.5) * 1.0;                    // perpendicular jitter
        d = min(d, sdSegment(p, prev, cur));         // distance to this segment
        prev = cur;
    }
    return d;
}

float sdSegment(vec2 p, vec2 a, vec2 b){
    vec2 pa = p-a, ba = b-a;
    float h = clamp(dot(pa,ba)/dot(ba,ba), 0.0, 1.0);
    return length(pa - ba*h);
}
```

## 2. Mathematics

### 2.1 The random walk

The arc is a **polyline** of $N$ segments. Each vertex is generated by a random walk:
$$
\mathbf v_{k+1}=\mathbf v_k+\boldsymbol\zeta_k,\qquad \boldsymbol\zeta_k\sim\text{jitter},
$$
where the jitter is a hash-driven random offset. For a "lightning bolt," the dominant direction is fixed (say +x), and the *perpendicular* jitter produces the zig-zag. The random walk gives the classic jagged, self-similar path: each segment is roughly straight but the whole path is jagged, and the jitter can be made *scale-invariant* (each level's jitter proportional to its step) for the fractal bolt.

### 2.2 Distance to a segment

Each segment $[\mathbf a,\mathbf b]$ contributes the point-to-segment distance (Chapter 3.4),
$$
d(\mathbf p,[\mathbf a,\mathbf b])=\lVert\mathbf p-(\mathbf a+h(\mathbf b-\mathbf a))\rVert,\qquad h=\operatorname{clamp}\frac{(\mathbf p-\mathbf a)\cdot(\mathbf b-\mathbf a)}{\lVert\mathbf b-\mathbf a\rVert^2}.
$$
The `min` over segments gives the distance to the **whole polyline**:
$$
d_{\text{arc}}(\mathbf p)=\min_k d(\mathbf p,[\mathbf v_k,\mathbf v_{k+1}]).
$$

**Field class.** This is a distance to a 1D set (a polyline), so it is 1-Lipschitz. It is a **valid distance bound** to the arc. The `min` (union) of segment distances is exact for the polyline (Chapter 9).

### 2.3 The glow

The bolt is colored with a bright core ($d$ small) and a soft glow (a `1/d`-style falloff, or a Gaussian $e^{-d^2}$). This is the same "inverse-distance glow" that we analyzed in Breakdown 9, but applied to a *true distance to a polyline* — so it is the *physically-motivated* version (the distance is real), not the hacky `1/D`.

### 2.4 Branching

For a real lightning bolt, add **branches**: at some probability, spawn a sub-arc from a point on the main arc at a random angle. This is a **recursive** structure. The distance is then the `min` over all branches (union of polylines).

## 3. The "thinking process"

1. **Ideas.** "I want a jagged electric arc." → a random-walk polyline.
2. **Jaggedness.** "Make it zig-zag." → jitter the perpendicular coordinate at each step.
3. **Distance.** "How far from the bolt?" → `min` of distance to each segment.
4. **Glow.** "Bright core, soft glow." → inverse-distance/Gaussian falloff.
5. **Branches.** "Add forks." → recursive sub-arcs.

## 4. Field-class analysis

| Stage | Operation | Class |
|-------|-----------|-------|
| random walk | stochastic path | n/a (geometry) |
| point-segment distance | exact distance | 1-Lipschitz |
| `min` over segments | union of segments | exact distance to polyline |
| glow | falloff on $d$ | color, not a field |

So the lightning bolt is a **true distance to a polyline**, and is therefore a legitimate 1-Lipschitz distance bound. This is a nice contrast to Breakdown 9: the "arc of light" can be exact if you make it the distance to a real walk path.

## 5. Extensions

- **Recursive branching.** Generate branches at random points/angles; the union distance handles them.
- **Animated time.** Re-seed the walk each frame (or walk *with* time) for flickering/arcing.
- **3D arcs.** Random walk in 3D and use segment SDFs in $\mathbb R^3$; the bolt can be a raymarchable object.
- **Field-driven jitter.** Replace the independent hash jitter with *curl-noise* jitter (Chapter 16) for a "flowing" discharge.
- **Electrical "flow".** Add a time-varying pulsation to the brightness (a `sin(iTime)` modulation) to simulate a discharge.
